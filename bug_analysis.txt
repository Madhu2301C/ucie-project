1. INCORRECT X/Z DETECTION IN ucie68b_flit_rx.sv (LINES 37-39)
================================================================================

  Current code:
    always_comb begin
        crc_error = (calculated_crc != received_crc);
        // The CRC recurrence may mask X/Z data; inspect its inputs as well.
        // synthesis translate_off
        if ((^crc_message === 1'bx) ||
            (^received_crc === 1'bx) || (^calculated_crc === 1'bx))
            crc_error = 1'b1;
        // synthesis translate_on
        flit_valid = !crc_error;
    end

  PROBLEM: The ^ operator is the reduction XOR, which XORs ALL bits together
  producing a single bit. For a 128-bit vector, ^crc_message gives 1 if an
  odd number of bits are '1', 0 if even. Comparing this single bit to
  1'bx only checks if the PARITY RESULT is X, NOT if any individual bit is X/Z.

  INTENDED BEHAVIOR: Detect if ANY bit in the vectors is X or Z, which would
  make the CRC comparison unreliable.

  FIX REQUIRED: Replace with proper X/Z detection, e.g.:
    if (|(crc_message === 1'bx) | (crc_message === 1'bz) |
        |(received_crc === 1'bx) | (received_crc === 1'bz) |
        |(calculated_crc === 1'bx) | (calculated_crc === 1'bz))
        crc_error = 1'b1;

  Example fix:
    always_comb begin
        crc_error = (calculated_crc != received_crc);
        if (crc_message === 1'bx || crc_message === 1'bz ||
            received_crc === 1'bx || received_crc === 1'bz ||
            calculated_crc === 1'bx || calculated_crc === 1'bz)
            crc_error = 1'b1;
        flit_valid = !crc_error;
    end

        payload_out !== message[527:16] ||

        dut.crc_message !== message)

  ANALYSIS: header_byte0 = flit_in[7:0] and header_byte1 = flit_in[15:8] (from

  THIS CHECK ALWAYS PASSES - it's comparing the extracted headers against the
  first 16 bits of the message, which by construction always match. This check
  provides no actual verification and should be replaced with a meaningful
  comparison, e.g., checking headers against known expected values or against
  the protocol fields.

4. CRC MESSAGE PADDING CONSISTENCY
================================================================================

  Current code in tb_ucie68b_flit_tx_mapping.sv lines 78-83:
    if (expected_crc_message[1023:528] !== '0)
        $fatal(1, "FAIL: expected CRC padding is not zero");

    if (dut.crc_message[1023:528] !== '0)
        $fatal(1, "FAIL: DUT CRC input padding is not zero");

  ANALYSIS: The CRC candidate (ucie_crc16_candidate.sv) processes ALL 1024 bits
  including bits [1023:528]. If these bits are X or Z, the CRC result may be
  undefined. The test correctly checks for zero padding, but the CRC candidate
  should ideally handle X/Z in padding bits gracefully (either by treating them
  as 0 or by flagging an error).

  VERIFICATION: The CRC reference (ucie_crc16_reference.sv) also processes all
  1024 bits (128 bytes × 8 bits). Both implementations need to ensure padding
  bits are consistently 0 before CRC calculation.
